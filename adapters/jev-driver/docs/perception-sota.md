## 1. Camera-only 3D detection / BEV perception

**Family map, not a single replacement.** Lift-Splat-Shoot lifts per-image features into depth frusta and splats them into a common BEV grid; BEVDet makes multi-camera BEV detection a practical pipeline. BEVFormer uses spatial cross-attention and temporal self-attention over BEV queries. PETR instead embeds 3D position into image features and decodes object queries. These are alternative internal representations; none requires the external consumer to accept its latent BEV tensor. [arxiv:2008.05711, **Lift, Splat, Shoot: Encoding Images From Arbitrary Camera Rigs by Implicitly Unprojecting to 3D**](https://arxiv.org/abs/2008.05711); [arxiv:2112.11790, **BEVDet: High-performance Multi-camera 3D Object Detection in Bird-Eye-View**](https://arxiv.org/abs/2112.11790); [arxiv:2203.17270, **BEVFormer: Learning Bird's-Eye-View Representation from Multi-Camera Images via Spatiotemporal Transformers**](https://arxiv.org/abs/2203.17270); [arxiv:2203.05625, **PETR: Position Embedding Transformation for Multi-View 3D Object Detection**](https://arxiv.org/abs/2203.05625).

Depth-supervised/temporal-stereo descendants include BEVDepth and BEVStereo. The sparse recurrent alternative includes StreamPETR, SparseBEV, and Sparse4D v3; it propagates compact object/query information rather than requiring a dense grid at the interface. RoPETR (2025) specifically targets StreamPETR velocity estimates; DenseBEV (2025) shows dense BEV continues rather than being entirely replaced. The 2026 Sparse4D journal extension explicitly covers multi-sensor temporal perception, so its results must not be silently labeled camera-only. [arxiv:2206.10092, **BEVDepth: Acquisition of Reliable Depth for Multi-view 3D Object Detection**](https://arxiv.org/abs/2206.10092); [arxiv:2209.10248, **BEVStereo: Enhancing Depth Estimation in Multi-view 3D Object Detection with Dynamic Temporal Stereo**](https://arxiv.org/abs/2209.10248); [arxiv:2303.11926, **Exploring Object-Centric Temporal Modeling for Efficient Multi-View 3D Object Detection**](https://arxiv.org/abs/2303.11926); [arxiv:2308.09244, **SparseBEV: High-Performance Sparse 3D Object Detection from Multi-Camera Videos**](https://arxiv.org/abs/2308.09244); [arxiv:2311.11722, **Sparse4D v3: Advancing End-to-End 3D Detection and Tracking**](https://arxiv.org/abs/2311.11722); [arxiv:2504.12643, **RoPETR: Improving Temporal Camera-Only 3D Detection by Integrating Enhanced Rotary Position Embedding**](https://arxiv.org/abs/2504.12643); [arxiv:2512.16818, **DenseBEV: Transforming BEV Grid Cells into 3D Objects**](https://arxiv.org/abs/2512.16818); [doi:10.1109/TPAMI.2026.3688545, **Sparse4D: Sparse-Based End-to-End Multi-Sensor Temporal Perception**](https://doi.org/10.1109/TPAMI.2026.3688545).

**Metric semantics matter more than one rank.** nuScenes mAP matches ground-plane centers at 0.5/1/2/4 m, not 3D IoU. NDS combines mAP (weight 5) with five clipped quality terms (weight 1 each): translation, scale, yaw, velocity and attributes. AMOTA evaluates multi-object tracking across recall operating points; it is not detection confidence or calibration. Waymo 3D detection ranks L2 mAPH over vehicle/pedestrian/cyclist, with heading-weighted precision and class-specific IoUs; its camera track instead ranks LET-3D-APL, allowing and penalizing longitudinal error. These metrics cannot be compared numerically as if identical. [arxiv:1903.11027, **nuScenes: A multimodal dataset for autonomous driving**](https://arxiv.org/abs/1903.11027); [arxiv:2008.08063, **AB3DMOT: A Baseline for 3D Multi-Object Tracking and New Evaluation Metrics**](https://arxiv.org/abs/2008.08063); [arxiv:2206.07705, **LET-3D-AP: Longitudinal Error Tolerant 3D Average Precision for Camera-Only 3D Detection**](https://arxiv.org/abs/2206.07705), plus the official protocols above.

**Implication for SceneObservation:** [DESIGN INFERENCE] normalize metric 3D centers, box dimensions, yaw/orientation, planar velocity, classes and optional attributes independently of BEV implementation; declare frame, SI units, coordinate convention, state time and causal history. Do not treat leaderboard NDS/AMOTA as per-object certainty; require uncertainty along depth/range, and never let future-frame autolabels masquerade as online observations.

## 2. Sensor fusion: camera, LiDAR and radar

BEVFusion unifies features in BEV, retaining camera semantic density otherwise lost in point-only projection. DeepInteraction instead maintains modality-specific representations with interaction. Successors include BEVFusion4D's cross-modal guidance/temporal aggregation, IS-Fusion's instance-and-scene context, SparseFusion and SparseLIF's sparse queries. Thus a modality-agnostic output is plausible even when internal fusion differs considerably. [arxiv:2205.13542, **BEVFusion: Multi-Task Multi-Sensor Fusion with Unified Bird's-Eye View Representation**](https://arxiv.org/abs/2205.13542); [arxiv:2208.11112, **DeepInteraction: 3D Object Detection via Modality Interaction**](https://arxiv.org/abs/2208.11112); [arxiv:2303.17099, **BEVFusion4D: Learning LiDAR-Camera Fusion Under Bird's-Eye-View via Cross-Modality Guidance and Temporal Aggregation**](https://arxiv.org/abs/2303.17099); [arxiv:2403.15241, **IS-Fusion: Instance-Scene Collaborative Fusion for Multimodal 3D Object Detection**](https://arxiv.org/abs/2403.15241); [arxiv:2304.14340, **SparseFusion: Fusing Multi-Modal Sparse Representations for Multi-Sensor 3D Object Detection**](https://arxiv.org/abs/2304.14340); [arxiv:2403.07284, **SparseLIF: High-Performance Sparse LiDAR-Camera Fusion for 3D Object Detection**](https://arxiv.org/abs/2403.07284).

**Modality contributions:** camera supplies dense appearance/semantics but uncertain depth; LiDAR supplies metric geometry and spatial priors; radar supplies range/Doppler features and radar cross section, but azimuth error and sparse returns complicate object localization. RCBEVDet explicitly uses RCS/Doppler, addresses misalignment by deformable cross-attention, and reports nuScenes test **63.9 NDS / 55.0 mAP** with V2-99. This supports improved kinematic estimation, not treating a radial Doppler reading as a full Cartesian velocity measurement. [arxiv:2205.13542, **BEVFusion: Multi-Task Multi-Sensor Fusion with Unified Bird's-Eye View Representation**](https://arxiv.org/abs/2205.13542); [arxiv:2403.16440, **RCBEVDet: Radar-camera Fusion in Bird's Eye View for 3D Object Detection**](https://arxiv.org/abs/2403.16440), body/Table 2 verified.

ReliFusion targets corruption/disconnection; GraphBEV++ targets calibration-induced misalignment; LiteFusion targets minimal adaptation and LiDAR absence. These 2025–2026 directions argue for exposing operational sensor availability and degraded coverage, not assuming fusion always dominates under failures. GaussianFusionOcc extends fusion to camera/LiDAR/radar occupancy rather than requiring three-modality boxes as the only output. [arxiv:2502.01856, **Reliability-Driven LiDAR-Camera Fusion for Robust 3D Object Detection**](https://arxiv.org/abs/2502.01856); [arxiv:2606.16354, **GraphBEV++: Multi-Modal Feature Alignment for Autonomous Driving**](https://arxiv.org/abs/2606.16354); [arxiv:2512.20217, **LiteFusion: Taming 3D Object Detectors from Vision-Based to Multi-Modal with Minimal Adaptation**](https://arxiv.org/abs/2512.20217); [arxiv:2507.18522, **GaussianFusionOcc: A Seamless Sensor Fusion Approach for 3D Occupancy Prediction Using 3D Gaussians**](https://arxiv.org/abs/2507.18522).

**Implication for SceneObservation:** [DESIGN INFERENCE] one common object-state schema plus `source_modalities`, source/model/version, active/degraded sensor status, time bounds and coverage; retain optional per-field provenance and uncertainty. Keep raw RCS, point count and pixel boxes in provider diagnostics, not mandatory reasoning inputs. Do not require brake lights, color, full 3D velocity or all-around visibility from every modality.

## 3. Occupancy / world-model perception

SurroundOcc predicts multi-camera 3D occupancy to handle arbitrary shape/classes beyond a box vocabulary. OpenOccupancy supplies surrounding semantic occupancy annotations/benchmarking; Occ3D supplies dense visibility-aware occupancy labels using densification and occlusion reasoning. These are evidence that a list of known-category boxes is not a complete model of collision-relevant space. [arxiv:2303.09551, **SurroundOcc: Multi-Camera 3D Occupancy Prediction for Autonomous Driving**](https://arxiv.org/abs/2303.09551); [arxiv:2303.03991, **OpenOccupancy: A Large Scale Benchmark for Surrounding Semantic Occupancy Perception**](https://arxiv.org/abs/2303.03991); [arxiv:2304.14365, **Occ3D: A Large-Scale 3D Occupancy Prediction Benchmark for Autonomous Driving**](https://arxiv.org/abs/2304.14365).

The family is moving beyond a static dense volume: Cam4DOcc forecasts future occupancy; StreamOcc streams dense voxels with motion alignment; UniOcc unifies prediction/forecasting across real datasets and simulators and includes voxel flow. GaussianOcc3D, ODG and GaussianFusionOcc explore sparse/continuous Gaussian representations; those Gaussians describe spatial primitives and **must not automatically be interpreted as calibrated object-state covariance**. [arxiv:2311.17663, **Cam4DOcc: Benchmark for Camera-Only 4D Occupancy Forecasting in Autonomous Driving Applications**](https://arxiv.org/abs/2311.17663); [arxiv:2503.22087, **Streaming Dense Voxel Representations for 3D Occupancy Prediction**](https://arxiv.org/abs/2503.22087); [arxiv:2503.24381, **UniOcc: A Unified Benchmark for Occupancy Forecasting and Prediction in Autonomous Driving**](https://arxiv.org/abs/2503.24381); [arxiv:2601.22729, **GaussianOcc3D: A Gaussian-Based Adaptive Multi-modal 3D Occupancy Prediction**](https://arxiv.org/abs/2601.22729); [arxiv:2506.09417, **ODG: Occupancy Prediction Using Dual Gaussians**](https://arxiv.org/abs/2506.09417); [arxiv:2507.18522, **GaussianFusionOcc: A Seamless Sensor Fusion Approach for 3D Occupancy Prediction Using 3D Gaussians**](https://arxiv.org/abs/2507.18522).

**Object-centric versus occupancy-centric for a text consumer — recommendation: hybrid, object-first.** [DESIGN INFERENCE] Object records cheaply preserve identity, kinematics, class ambiguity and human-relevant relations. PlanT and the object-vector LLM paper support the usefulness of compact objects for reasoning/planning, though not a Jev safety guarantee. Dense occupancy retains geometry of debris, overhangs, unclassified surfaces and free-space/unknown distinctions that boxes lose. Therefore let the deterministic collision checker retain detailed occupancy, and serialize a compact set of hazardous occupied regions plus **unknown/occluded regions and observed free corridors**, alongside tracks. Do not force every occupied patch into a fictitious tracked car, and do not equate an empty object list with free space. [arxiv:2210.14222, **PlanT: Explainable Planning Transformers via Object-Level Representations**](https://arxiv.org/abs/2210.14222); [arxiv:2310.01957, **Driving with LLMs: Fusing Object-Level Vector Modality for Explainable Autonomous Driving**](https://arxiv.org/abs/2310.01957); occupancy provenance as above.

**[DESIGN INFERENCE] Why not serialize the voxel tensor?** A 200×200×16 grid has 640,000 cells before probabilities, semantics, times or JSON overhead (arithmetic example, not a measured token result). Flattening this for a text model expends context while obscuring identity and relations. Conversely, compressing it into “road clear” discards the very unknown-space and obstacle evidence that motivated occupancy. Use bounded polygons/corridors with vertical extent, known coverage, optional calibrated occupancy probability, resolution and generation time. Predicted future occupancy must be separately labeled by horizon and motion-model assumptions, not presented as current observation.

**Implication for SceneObservation:** object tracks are the default reasoning interface; add optional `occupied_regions`, `observed_free_regions`, `unknown_regions`, `coverage`, and separately typed future occupancy/flow. Every region needs frame, geometry in meters, vertical bounds, time and provenance; omission means unsupported/unobserved, not empty/free.

## 4. 3D multi-object tracking and state estimation — priority contract

**Separate existence, class, localization, and lifecycle.** A detection score is not automatically a posterior probability that an object exists. In a random-finite-set tracker a Bernoulli component has existence probability `r ∈ [0,1]` and a state density conditional on existence, commonly Gaussian `N(mean, covariance)`; a Poisson intensity represents the not-yet-detected population, while mixture weights represent alternative global associations. The driving implementation distinguishes detected/undetected populations, uses constant-velocity dynamics, retains track IDs, and even incorporates detector scores when initializing existence: this incorporation is a modeling choice, not proof that scores were calibrated. [arxiv:2103.07783, **Multi-Object Tracking using Poisson Multi-Bernoulli Mixture Filtering for Autonomous Vehicles**](https://arxiv.org/abs/2103.07783); [arxiv:1703.04264, **Poisson multi-Bernoulli mixture filter: direct derivation and implementation**](https://arxiv.org/abs/1703.04264).

**Gaussian-filter baseline remains relevant.** AB3DMOT uses 3D Kalman filtering plus Hungarian association; probabilistic 3D MOT estimates initial/process/measurement covariance from training statistics and uses stochastic information in association. Thus a stack can produce a posterior covariance even if its detector never predicts one. That covariance is conditional on motion/noise/association assumptions; it is not an omniscient error bound. SimpleTrack explicitly decomposes preprocessing, association, motion model, and lifecycle management. [arxiv:2008.08063, **AB3DMOT: A Baseline for 3D Multi-Object Tracking and New Evaluation Metrics**](https://arxiv.org/abs/2008.08063); [arxiv:2001.05673, **Probabilistic 3D Multi-Object Tracking for Autonomous Driving**](https://arxiv.org/abs/2001.05673); [arxiv:2111.09621, **SimpleTrack: Understanding and Rethinking 3D Multi-object Tracking**](https://arxiv.org/abs/2111.09621).

**Not all boxes have jointly estimated uncertainty.** The PMBM driving paper tracks compressed center states and copies box dimensions from detections; do not imply that every emitted size or orientation has a filter covariance. Uncertainty-Aware AB3DMOT explicitly connects variational detector uncertainty to tracking, whereas sparse learned perception can assign instance IDs without exporting an explicit Gaussian state posterior. [arxiv:2103.07783, **Multi-Object Tracking using Poisson Multi-Bernoulli Mixture Filtering for Autonomous Vehicles**](https://arxiv.org/abs/2103.07783); [arxiv:2302.05923, **Uncertainty-Aware AB3DMOT by Variational 3D Object Detection**](https://arxiv.org/abs/2302.05923); [arxiv:2311.11722, **Sparse4D v3: Advancing End-to-End 3D Detection and Tracking**](https://arxiv.org/abs/2311.11722).

**Modern neighbors rather than a universal convention.** GNN-PMB and OptiPMB continue the interpretable RFS family. CANMOT revisits the assumption of class-independent process/measurement noise and proposes class-aware, object-aligned covariances. This is evidence against hard-coding one global scalar accuracy for all vehicles/pedestrians, but not evidence every deployed tracker emits these fields. [arxiv:2206.10255, **GNN-PMB: A Simple but Effective Online 3D Multi-Object Tracker without Bells and Whistles**](https://arxiv.org/abs/2206.10255); [arxiv:2503.12968, **OptiPMB: Enhancing 3D Multi-Object Tracking with Optimized Poisson Multi-Bernoulli Filtering**](https://arxiv.org/abs/2503.12968); [arxiv:2606.03590, **CANMOT: Class-Aware Noise Modeling for Multi-Object Tracking in Autonomous Driving**](https://arxiv.org/abs/2606.03590).

**[DESIGN INFERENCE] Parameterization:** distinguish `detection_score` (opaque ranking score with definition), nullable `existence_probability` (posterior Bernoulli semantics), and nullable `class_probabilities` (distribution conditional on the object's existence). Use `track_id` scoped to provider/session, `first_seen_time_s`, `last_observed_time_s`, `state_time_s`, `track_status: tentative|confirmed|coasting`, and optional observation count. Age is elapsed time, not evidence strength or guaranteed identity. IDs can switch or reset. Keep a covariance object `{state_order, matrix, frame, conditioning, method}`; a useful planar order is `[x,y,vx,vy]`, with SI units and entries in products of component units. A 3D order `[x,y,z,vx,vy,vz]` is optional, not mandatory. Cross terms matter; a zero off-diagonal must mean an explicit independence approximation, not missing data. Yaw needs wrapping/circular semantics; do not silently place a Gaussian across the ±π discontinuity. A mixture or samples can be an extension for multimodal association/state uncertainty. These are normalization recommendations from the above filter families, not a standard implemented identically by all trackers.

**Implication for SceneObservation:** make identity/lifecycle and **typed, nullable uncertainty** first-class; preserve `state_time_s` versus `last_observed_time_s`; separate `existence_probability`, `class_probabilities`, and `detection_score`; encode covariance variable order/frame/units explicitly; never invent covariance from `1-score`, and never replace unavailable covariance with zero.

## 5. Detector uncertainty and calibration

**Probabilistic detection is available, not universal.** Bayesian/variational detectors distinguish aleatoric observation ambiguity from epistemic model uncertainty; heteroscedastic regression predicts input-dependent dispersion, and variational detection can propagate uncertainty into a tracker. These are optional capabilities that an ordinary point-estimate detector does not gain by renaming its score. [arxiv:1804.05132, **Towards Safe Autonomous Driving: Capture Uncertainty in the Deep Neural Network For Lidar 3D Vehicle Detection**](https://arxiv.org/abs/1804.05132); [arxiv:1809.05590, **Leveraging Heteroscedastic Aleatoric Uncertainties for Robust Real-Time LiDAR 3D Object Detection**](https://arxiv.org/abs/1809.05590); [arxiv:2302.05923, **Uncertainty-Aware AB3DMOT by Variational 3D Object Detection**](https://arxiv.org/abs/2302.05923).

**Confidence is demonstrably miscalibrated.** A probabilistic LiDAR detector models classification scores and Gaussian regression marginals including position offsets, sine/cosine heading and log dimensions. The calibration study finds that improved detection accuracy does not ensure improved uncertainty estimation; temperature scaling, isotonic regression, and a calibration loss help. In its nuScenes transfer experiment, averaged ECE is **0.218 uncalibrated**, **0.126** with KITTI-fit temperature scaling, **0.120** with KITTI-fit isotonic regression, and **0.078 / 0.030** when fitting the respective methods on 1% of nuScenes data. These numbers concern that detector and its averaged classification/regression ECE, not modern nuScenes mAP and not a universal residual error rate. [arxiv:1909.12358, **Can We Trust You? On Calibration of a Probabilistic Object Detector for Autonomous Driving**](https://arxiv.org/abs/1909.12358), targeted full-text verification, Table III.

**New work keeps the problem open.** Calibration of the whole class vector is distinct from calibration only of the top prediction. Query2Uncertainty explicitly addresses distribution-shift failures of ordinary post-hoc calibration. Conformal multimodal fusion is a neighboring alternative to Monte-Carlo uncertainty estimation, but its guarantees must not be assumed to survive arbitrary domain shift. [arxiv:2510.01829, **Calibrating the Full Predictive Class Distribution of 3D Object Detectors for Autonomous Driving**](https://arxiv.org/abs/2510.01829); [arxiv:2605.05328, **Query2Uncertainty: Robust Uncertainty Quantification and Calibration for 3D Object Detection under Distribution Shift**](https://arxiv.org/abs/2605.05328); [arxiv:2309.09593, **Mutual Information-calibrated Conformal Feature Fusion for Uncertainty-Aware Multimodal 3D Object Detection at the Edge**](https://arxiv.org/abs/2309.09593).

**[DESIGN INFERENCE] RLCD is not a repair operation for perception.** Jev's calibrated decision training does not establish calibration on JSON from a new detector or after changing filtering thresholds. A probability conditional on incorrect scene evidence is not automatically a calibrated real-world event probability. Keep calibrated versus raw score semantics explicit; assess the composed pipeline on held-out scenes, including missing objects and stale tracks. Evaluate existence/class reliability and proper scoring rules separately from state-distribution coverage, with domain/range/class/visibility strata. Do not multiply Jev confidence by detector score as an invented probability calculus. The empirical motivation is the calibration/transfer study above, not a paper evaluating Jev.

**Implication for SceneObservation:** add calibration metadata (`method`, `model_version`, `calibration_dataset/domain`, `calibration_version`, `status: calibrated|uncalibrated|unknown`) and uncertainty provenance; allow aleatoric/epistemic decomposition only when supported; do not interpret a detector rank score, IoU-quality score, or Jev distribution-concentration statistic as existence probability.

## 6. Sim-to-real transfer and perception domain gap

**Real-to-real adaptation is not itself sim-to-real evidence.** ST3D and ST3D++ use random object scaling, quality-aware pseudo labels, memory and denoised self-training; these support adapting a detector to a target distribution, not a promise that clean simulator truth trains a deployment-ready policy. CTS specifically addresses synthetic-to-real detection and compares these methods. [arxiv:2103.05346, **ST3D: Self-training for Unsupervised Domain Adaptation on 3D Object Detection**](https://arxiv.org/abs/2103.05346); [arxiv:2108.06682, **ST3D++: Denoised Self-training for Unsupervised Domain Adaptation on 3D Object Detection**](https://arxiv.org/abs/2108.06682); [arxiv:2406.18129, **CTS: Sim-to-Real Unsupervised Domain Adaptation on 3D Detection**](https://arxiv.org/abs/2406.18129).

**Quantified detection transfer:** CTS Table I, PointRCNN-based car detection, AP3D at IoU 0.7:

| Synthetic→real evaluation, moderate difficulty | Source-only | ST3D++ adaptation | CTS adaptation | Target-supervised oracle |
|---|---:|---:|---:|---:|
| CARLA3D→KITTI | 4.06 | 27.22 | 45.28 | 71.70 |
| CARLA3D→Lyft | 13.85 | 37.24 | 45.87 | 66.05 |

Source: [arxiv:2406.18129, **CTS: Sim-to-Real Unsupervised Domain Adaptation on 3D Detection**](https://arxiv.org/abs/2406.18129), body/Table I verified. These are AP percentage points, not success rates on roads. KITTI source-only is 67.64 points below target-supervised; even CTS remains 26.42 points below (arithmetic from the table). Source-only versus oracle is a domain/training comparison, not a paired clean/noisy-policy experiment.

**Even scenario matching leaves a gap.** A matched-real/sim LiDAR investigation trains PointRCNN and PointPillars five times and reports about **14 AP points** sim-to-real difference, reduced to about **10 points** with simulated ray-direction Gaussian noise (2 cm standard deviation); downsampling did not improve the gap. The study uses simple scenarios and one detected class, so it cannot establish universal transfer percentages. [arxiv:2303.01899, **Quantifying the LiDAR Sim-to-Real Domain Shift: A Detailed Investigation Using Object Detectors and Analyzing Point Clouds at Target-Level**](https://arxiv.org/abs/2303.01899), body verified.

**Downstream policies need error models, not just box jitter.** EMPERROR models context-dependent false positives, false negatives and regression errors, showing limitations of fixed Gaussian/object-independent noise. On nuScenes validation with an imitation planner, Table II reports open-loop collision rate for BEVFormer outputs **3.20%**, its learned perception error model **3.36%**, and adversarial errors with κ=3 **6.20%** (+85% relative to the non-adversarial error-model value). StreamPETR equivalents are **3.40%, 3.58%, 6.28%**. This is a measured perception-error sensitivity, **not** an on-road closed-loop collision rate and **not** a clean-ground-truth versus real-perception drop. [arxiv:2411.07719, **EMPERROR: A Flexible Generative Perception Error Model for Probing Self-Driving Planners**](https://arxiv.org/abs/2411.07719), Table II verified.

Related planning-oriented evaluations explicitly ask how perceptual errors affect driving rather than assuming detection metrics suffice; newer closed-loop robustness work includes latency and ego-state perturbations. The search did **not** establish a controlled real-road experiment proving that a ground-truth-trained text-only decision policy survives swapping in noisy perception unchanged. [arxiv:2306.07276, **Transcendental Idealism of Planner: Evaluating Perception from Planning Perspective for Autonomous Driving**](https://arxiv.org/abs/2306.07276); [arxiv:2605.18059, **Bench2Drive-Robust: Benchmarking Closed-Loop Autonomous Driving under Deployment Perturbations**](https://arxiv.org/abs/2605.18059).

**Implication for SceneObservation:** [DESIGN INFERENCE] use identical semantics but distinct truth/estimated provenance; a provider capability profile must expose unsupported fields. Evaluate clean truth, visibility-limited truth, detector-like correlated errors/dropouts/duplicates/ID switches, stale timestamps and real detector replay separately. Domain portability of the JSON type does not imply distribution portability or safety.

## 7. End-to-end versus modular AV stacks

**Evidence against simplistic modularity:** UniAD argues sequential independent tasks accumulate error and optimizes perception/prediction/occupancy/planning together through task interactions. VAD uses vectorized agents/maps as explicit planning constraints while still training end-to-end. UAD argues costly supervised intermediate subtasks impose annotation and architectural burdens. These challenge the claim that hand-designed object JSON is necessarily sufficient or optimal; task-relevant information can be lost at a hard interface. [arxiv:2212.10156, **Planning-oriented Autonomous Driving**](https://arxiv.org/abs/2212.10156); [arxiv:2303.12077, **VAD: Vectorized Scene Representation for Efficient Autonomous Driving**](https://arxiv.org/abs/2303.12077); [arxiv:2406.17680, **End-to-End Autonomous Driving without Costly Modularization and 3D Manual Annotation**](https://arxiv.org/abs/2406.17680).

**Evidence supporting structured interfaces/hybrid reasoning:** PlanT demonstrates compact object-level planning representations; PDM's study emphasizes short-horizon rule-based priors and distinguishes closed-loop planning from long-horizon forecasting. Hybrid imitation/optimization combines learned behavior with short-horizon optimization. These support explicit geometry and independent checks, but do not directly validate natural-language/JSON decision layers or prove modular superiority with noisy sensors. [arxiv:2210.14222, **PlanT: Explainable Planning Transformers via Object-Level Representations**](https://arxiv.org/abs/2210.14222); [arxiv:2306.07962, **Parting with Misconceptions about Learning-based Vehicle Motion Planning**](https://arxiv.org/abs/2306.07962); [arxiv:2409.02871, **Hybrid Imitation-Learning Motion Planner for Urban Driving**](https://arxiv.org/abs/2409.02871).

**Evaluation caveat cuts both ways:** ego-status shortcuts can make open-loop nuScenes planning deceptively good without adequate perception; interPlan challenges generalization to unusual interactive scenarios even for planners strong on nuPlan. Neither an open-loop L2 improvement nor a QA accuracy improvement establishes closed-loop collision avoidance. A 2025 study additionally reports negative transfer when semantics and motion are forced into one representation, supporting investigation of separation rather than insisting joint learning always wins. [arxiv:2312.03031, **Is Ego Status All You Need for Open-Loop End-to-End Autonomous Driving?**](https://arxiv.org/abs/2312.03031); [arxiv:2404.07569, **Can Vehicle Motion Planning Generalize to Realistic Long-tail Scenarios?**](https://arxiv.org/abs/2404.07569); [arxiv:2502.07631, **Divide and Merge: Motion and Semantic Learning in End-to-End Autonomous Driving**](https://arxiv.org/abs/2502.07631).

**Implication for SceneObservation:** [DESIGN INFERENCE] choose modularity for inspectable contracts, provider replacement and deterministic safety ownership, not because the literature proves text sufficiency. Preserve geometric/uncertainty information outside the text compression, and evaluate complete closed-loop behavior under perception errors; Jev selects among code-generated candidates and cannot replace collision checking or unknown-space handling.

## 8. Language/text interfaces to driving scenes

**Closest object-level precedent, but not a drop-in JSON result:** Driving with LLMs encodes compact numeric vectors for route, vehicles, pedestrians and ego state through learned vector encoders and a Vector Former, aligns them to structured language, and trains on 160k QA pairs from 10k simulation scenarios. Its appendix lists relative ego-frame position/orientation, speed, dimensions, vehicle class/corners, route geometry/speed limits/lights, and ego dynamics. Crucially, it also contains simulator pedestrian crossing intent: **do not copy this privileged field into a mandatory real-perception schema**. This learned numeric-modality adapter is unavailable to text-only Jev, and the paper does not establish that plain JSON retains its performance under real detector noise. [arxiv:2310.01957, **Driving with LLMs: Fusing Object-Level Vector Modality for Explainable Autonomous Driving**](https://arxiv.org/abs/2310.01957), body and Appendix B verified.

**Graph and annotation-generated QA:** DriveLM organizes perception→prediction→planning through graph-structured visual QA, providing a precedent for stable object references and relationships, not for independent questions magically sharing answers. NuScenes-QA constructs a multimodal driving VQA benchmark; its annotation-driven questions do not prove that a real detector can recover every requested attribute. [arxiv:2312.14150, **DriveLM: Driving with Graph Visual Question Answering**](https://arxiv.org/abs/2312.14150); [arxiv:2305.14836, **NuScenes-QA: A Multi-modal Visual Question Answering Benchmark for Autonomous Driving Scenario**](https://arxiv.org/abs/2305.14836).

**Contrasting multimodal systems:** LMDrive uses multimodal sensor tokens plus language for closed-loop driving; DriveGPT4 consumes multi-frame video and textual questions, producing explanations/actions. TOKEN explicitly tokenizes object-level knowledge for long-tail planning; OpenDriveVLA aligns 2D/3D instance-aware visual representations with language and ego state. All are relevant representations, but none is evidence that a frozen, text-only calibrated judgment model accepts visual embeddings or matches their driving performance. [arxiv:2312.07488, **LMDrive: Closed-Loop End-to-End Driving with Large Language Models**](https://arxiv.org/abs/2312.07488); [arxiv:2310.01412, **DriveGPT4: Interpretable End-to-end Autonomous Driving via Large Language Model**](https://arxiv.org/abs/2310.01412); [arxiv:2407.00959, **Tokenize the World into Object-level Knowledge to Address Long-tail Events in Autonomous Driving**](https://arxiv.org/abs/2407.00959); [arxiv:2503.23463, **OpenDriveVLA: Towards End-to-end Autonomous Driving with Large Vision Language Action Model**](https://arxiv.org/abs/2503.23463).

**Numeric/token efficiency is unresolved for this interface.** DriveCode studies numerical-token precision/efficiency limitations and specialized encodings. That is a caution about serialization, not a measured optimal JSON format for Jev. This search did not establish a controlled driving study comparing equally informative plain JSON versus terse prose versus arrays, with a token-budget/closed-loop-safety curve. Numeric-vector and visual-token counts are not interchangeable with tokenizer counts for decimal JSON. [arxiv:2603.00919, **DriveCode: Domain Specific Numerical Encoding for LLM-Based Autonomous Driving**](https://arxiv.org/abs/2603.00919).

**[DESIGN INFERENCE] Recommended serialization:** one compact typed scene, stable track references, documented units/frame, bounded relevant objects, and code-computed relations (`distance`, `relative_velocity`, `lane_relation`) where their provenance is clear. Do not truncate hazards solely by class confidence or distance; surface omitted-region/coverage metadata. Round to justified sensor resolution rather than printing floating-point noise. Prefer explicit `unknown`/nullable values over omitted facts that look like negative observations. Keep geometry/collision checking in code; supply Jev already-vetted candidate summaries. Benchmark alternate serializations against the same noisy scenes and candidate judgments before claiming token savings preserve decisions.

**Implication for SceneObservation:** use object-centric JSON with stable references and uncertainty/age/coverage; optional relationship records can support language reasoning; do not serialize learned visual tokens, raw voxel grids, privileged intent, or unsupported attributes as facts; token-cost versus retention needs a local controlled experiment, not a borrowed multimodal score.

## Recommended schema fields, with provenance

The field names below are **[DESIGN INFERENCE]**, not claims of a universal published standard. Capability is tiered: **core** means normalize what a box detector ordinarily exports; **optional** means obtainable by an appropriate tracker/occupancy/map/attribute subsystem; **unavailable** means no reliable factual source in generic real perception. The same JSON type must allow missing capabilities without fabricating values.

**[DESIGN INFERENCE] Covariance transformation:** when rotating a state, transform covariance consistently (`P_new = J P_old Jᵀ`); a rotating ego coordinate system and uncertain ego pose can introduce further terms and shared correlations. Do not merely rotate means and retain axis-aligned variances. Simulator truth may use exact probability 1 / covariance zero **only within the simulator's declared truth semantics**, not as a claim of perfect real sensing or guaranteed future safety. Sensor-emulated truth must respect visibility and must not expose IDs/objects that the emulated observer has never seen. Motivation: the conditional Gaussian/RFS states and explicit undetected populations of [arxiv:2103.07783, **Multi-Object Tracking using Poisson Multi-Bernoulli Mixture Filtering for Autonomous Vehicles**](https://arxiv.org/abs/2103.07783).

### Fields real perception cannot reliably supply as facts

- **True crossing intent, destination, planned maneuver, driver attention or willingness to yield.** Future behavior is prediction, not measurement. The simulator vector paper includes crossing intent; its availability there is precisely a leakage risk. [arxiv:2310.01957, **Driving with LLMs: Fusing Object-Level Vector Modality for Explainable Autonomous Driving**](https://arxiv.org/abs/2310.01957); [arxiv:2212.10156, **Planning-oriented Autonomous Driving**](https://arxiv.org/abs/2212.10156).
- **Guaranteed absence behind occluders/outside the observed domain, or identities/states of never-observed hidden actors.** Keep unknown space or an undetected-population model instead. [arxiv:2103.07783, **Multi-Object Tracking using Poisson Multi-Bernoulli Mixture Filtering for Autonomous Vehicles**](https://arxiv.org/abs/2103.07783); [arxiv:2304.14365, **Occ3D: A Large-Scale 3D Occupancy Prediction Benchmark for Autonomous Driving**](https://arxiv.org/abs/2304.14365).
- **Perfect persistent physical identity, exact pose/size/velocity/acceleration, true estimation error, universally calibrated covariance, or guaranteed calibrated existence from a detector score.** These are estimates/assumptions with association errors and calibration gaps. [arxiv:2111.09621, **SimpleTrack: Understanding and Rethinking 3D Multi-object Tracking**](https://arxiv.org/abs/2111.09621); [arxiv:1909.12358, **Can We Trust You? On Calibration of a Probabilistic Object Detector for Autonomous Driving**](https://arxiv.org/abs/1909.12358).
- **Brake-light/turn-signal/traffic-light state, emergency status, right-of-way, lane assignment, friction or speed limit from every generic 3D detector.** Some can be estimated by dedicated appearance/map/vehicle subsystems, but they are not the standard box/velocity/class output. Treat absence of capability as unknown; in particular, “unknown signal” is not “green.” This is a scope conclusion from [arxiv:1903.11027, **nuScenes: A multimodal dataset for autonomous driving**](https://arxiv.org/abs/1903.11027) and [arxiv:2303.12077, **VAD: Vectorized Scene Representation for Efficient Autonomous Driving**](https://arxiv.org/abs/2303.12077), not a claim that visual attribute estimation is impossible.

## Search coverage, thin results and unresolved questions

- **Index search coverage:** distinct framings covered Bayesian/RFS tracking; detector calibration; graph QA and vector-language interfaces; BEV camera detection; radar/LiDAR fusion; dense/sparse occupancy; sim-to-real adaptation; perception-error planning; modular/end-to-end evaluation; Waymo metrics. Strong anchors were expanded with `related-papers` in **similar** mode (PMBM/GNN-PMB), **references** mode (DriveLM/object-vector LLM) and **citers** mode (Sparse4D/StreamPETR). Canonical metadata was inspected for PETR, VAD, nuScenes, the 2026 Sparse4D extension and the recent nuScenes retrospective. Load-bearing quantities/parameterizations were checked through `read-paper`.
- **Thin current-ranking results:** “2025/2026 camera-only nuScenes/Waymo SOTA” repeatedly returned earlier anchors and neighboring tasks. Later methods are included where relevant, but a complete current rank ordering was not recovered. Official pages expose metrics but their reader-extracted leaderboard rows are empty; a guessed Waymo 2025 detection URL returned 404, corrected by following the official challenges index. No 2026 winner is invented; reference metrics are dated/setup-specific.
- **Thin plain-JSON serialization evidence:** object-vector/visual-token methods are abundant, controlled JSON-versus-prose/array studies tied to token cost and safe closed-loop driving are not established. No claimed optimal token budget or guaranteed information-preserving compression.
- **Thin clean-truth-policy→real-road-noisy-perception transfer evidence:** measurable detection gaps and planner error sensitivity were found, but not a universal drop or a real-road validation of a truth-trained text-only Jev policy. EMPERROR's numbers are open-loop and adversarial-model comparisons, explicitly not that missing experiment.
- **Unresolved production convention:** research implementations demonstrate existence probabilities, full/diagonal covariance, learned query tracks and calibration methods; they do not establish which commercial AV stack exposes each field, or a universally calibrated cross-provider posterior.
- **Unresolved calibration composition:** no retrieved paper evaluates Jev/RLCD conditional on a changed perception provider. Downstream calibration must be tested on the composed system; ordinary detector score calibration is not sufficient evidence.
- **Unresolved coverage/unknown-space guarantees:** occupancy predicts geometric support but does not establish certified free space or calibrated probability of every hidden actor. Preserve unknowns rather than manufacturing certainty.

No Simforge code was changed. This research artifact is for schema design and simulation evaluation, not public-road deployment approval.
